# gamesour.com — website analysis (read-only, public pages only)

Target: `https://gamesour.com` — a Bangladeshi game top-up / gift-voucher store.
Method: fetched public pages and the site's own public metadata files. No login,
no payment attempt, no admin probing, no scanning, no automated crawling.

**Honest limit up front:** this sandbox cannot open a raw HTTPS connection to
`gamesour.com` (egress is restricted), and no browser is installed. I reached
the site through a page-fetch service, which returns *rendered text*, not the
raw HTML or JavaScript bundles. So this report describes **observable
architecture and behaviour**, not source code. Anything requiring the JS
bundles is listed in section 8 as a known gap.

---

## 1. Confirmed stack

| Layer | Finding | How it was confirmed |
| --- | --- | --- |
| Frontend framework | **Nuxt 3** (Vue 3), server-side rendered | `/_nuxt/` asset paths; `/_nuxt/builds/latest.json` returned `{"id":"11809bdd-…"}`; unknown routes return a page titled `404 - Page not found: /api \| Nuxt` |
| Build | Vite (inferred from Nuxt 3) | inference, not directly observed |
| SSR | Active — pages arrive with content already in the HTML | product pages returned full text to a non-JS fetcher |
| Payload extraction | **Disabled** | `/_payload.json` returned only `[{"data":-1,"prerenderedAt":-1}]` |
| Backend | Separate service behind `/api/*` | Nuxt route rules redirect `/robots.txt` → `/api/robots.txt` and `/sitemap.xml` → `/api/sitemap.xml`; those are generated by the backend, not static files |
| CMS / asset host | `admin.gamesour.com` | banners: `/banners/<ts>.png`, products: `/products/<ts>.jpg`, notices: `/notices/<ts>_<name>.png` |
| Build freshness | current build id `11809bdd-0af1-413b-b82c-ab790f928f8a`, timestamp 1785919458934 | from `latest.json` |

Two hosts, two jobs: `gamesour.com` renders the storefront; `admin.gamesour.com`
serves media and likely hosts the admin panel that creates the content.

Note the timestamp-based filenames (`1747164701.png`). That is a common pattern
where uploads are stored as `<unix-timestamp>.<ext>` — meaning those images are
served from a public directory on the admin host.

## 2. Route map

From `sitemap.xml` plus links found on pages:

| Route | Purpose |
| --- | --- |
| `/` | homepage: notice bar, banner carousel, product sections, live order feed |
| `/topup` | top-up catalogue |
| `/shop` | shop catalogue (**client-rendered** — returned empty to a non-JS fetch) |
| `/topup/{id}/{slug}` | a top-up product, e.g. `/topup/128/null` (Level Up Pass), `/topup/109/123123`, `/topup/999/ff-like` |
| `/giftvoucher/{id}/{slug}` | gift voucher product, e.g. `/giftvoucher/119/Shell`, `/giftvoucher/80/12321` |
| `/login`, `/register` | authentication |
| `/contactus` | contact |

The `{id}/{slug}` pattern matters: the **numeric ID is the real key**, and the
slug is cosmetic. `null` and `123123` are both used as slugs, which proves the
app resolves products by ID and ignores the slug. That is a reasonable design,
but it means slugs can never be relied on for SEO or for validating a URL.

## 3. The ordering flow (the core feature)

Every product page is the same three-step wizard, with numbered headings:

**Step 1 — "Select Recharge"**: package list with price in ৳, e.g.

```
WEEKLY PREMIUM        154 TK
MONTHLY DISCOUNT      770 TK
Weekly prmium2x       308 TK
Monthly 2x            1540 TK
2530 DIAMOND          1590 TK
```

**Step 2 — "Account Info"**: a text field for the game UID, with a hint link
("check your game ID name"). For vouchers, step 2 is a **quantity** field
instead.

**Step 3 — "Select one option"**: two payment routes —

- **Wallet Pay** — pay from an in-site balance
- **Instant Pay** — pay per order, directly

Then a computed total (`প্রোডাক্ট কিনতে আপনার প্রয়োজন 0 টাকা` = "you need 0 TK"),
a login gate ("Please Login To Purchase"), and a "Rules & Conditions" block.

**Business rules visible in the page text:**

- Orders per user capped at **5 packages per 24 hours**
- Premium tier unlocks after **৳20,000 lifetime spend**, unlocking discounted
  products ("this product only unlocks for special users")
- Products can show **STOCK OUT** — so a package has stock/availability state
- One product was gated behind login, another showed a price of 0 TK

That last point is worth flagging honestly: a 0 TK total on a logged-out view is
most likely "nothing selected yet", not a real price. I am labelling it an
unexplained observation, not a pricing bug.

## 5. Homepage composition

1. **Notice bar** — a Bengali announcement about automated UID delivery, plus a
   warning that orders paid with stolen money will be reported
2. **Banner carousel** — one banner repeated three times, all linking to
   `https://appegy.xyz/gamesour.apk`
3. **Product sections** — "LEVEL UP PASS PRODUCT", "HOT DEALS ⚡",
   "Raguler TopUp ⚡", "GARENA SHELL", each a row of product cards
4. **Recent Orders feed** — a live list showing user name, avatar, product,
   price in ৳, timestamp and a "✓ Done" status, with relative times in Bengali
   ("৯ মিনিট আগে" = 9 minutes ago)
5. **Support** — Telegram link to `t.me/games_our`

The live order feed is a deliberate trust feature: showing real purchases
reduces buyer hesitation. It also leaks customer names and purchase amounts to
every visitor — a privacy decision the operators made.

## 6. Two things a buyer should know

**a) The APK is hosted off-site.** Every banner points to
`https://appegy.xyz/gamesour.apk` — a domain unrelated to `gamesour.com`.
Installing an APK from an unconnected host is a real risk (it could be swapped
at any time). If you build a similar store, ship your app from your own domain
over HTTPS, and ideally publish through Play.

**b) The voucher page text is copied from another site.** The "What is Garena
Shells" section on `/giftvoucher/119/Shell` repeatedly names **Jubaly.com** and
links to `jubaly.com/product/garena-shell-bd/`, describing "buying from
Jubaly.com". That text is duplicated from a competitor, including the payment
method list (bKash, Nagad, Rocket, Okwallet, Upay, Tap).

That means: **do not treat that payment-method list as gamesour's own.** It is
evidence of copy-paste, not of their integration. For your own site, copied
boilerplate carries SEO-duplication and copyright risk.

## 7. Rebuilding this in PHP — the transferable architecture

Ignore the visual design; the *information architecture* is what is worth
copying, and it is simple.

**Database sketch**

```sql
-- products are one table with a type, so /topup and /giftvoucher share code
CREATE TABLE products (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  type          ENUM('topup','giftvoucher') NOT NULL,
  slug          VARCHAR(96) NULL,          -- cosmetic only; id is the key
  title         VARCHAR(128) NOT NULL,
  image_path    VARCHAR(255),
  rules_html    MEDIUMTEXT,                -- "Rules & Conditions" block
  is_active     TINYINT(1) DEFAULT 1,
  min_lifetime_spend INT DEFAULT 0          -- 20000 for premium-gated products
);

CREATE TABLE packages (                     -- step 1 list
  id          INT AUTO_INCREMENT PRIMARY KEY,
  product_id  INT NOT NULL,
  label       VARCHAR(96) NOT NULL,         -- "WEEKLY PREMIUM"
  price_bdt   DECIMAL(10,2) NOT NULL,
  stock       INT NOT NULL DEFAULT 0,       -- 0 => show STOCK OUT
  FOREIGN KEY (product_id) REFERENCES products(id)
);

CREATE TABLE orders (
  id           INT AUTO_INCREMENT PRIMARY KEY,
  user_id      INT NOT NULL,
  package_id   INT NOT NULL,
  game_uid     VARCHAR(64),                 -- step 2 (null for vouchers)
  quantity     INT NOT NULL DEFAULT 1,
  amount_bdt   DECIMAL(10,2) NOT NULL,
  pay_method   ENUM('wallet','instant') NOT NULL,
  status       ENUM('pending','paid','delivered','cancelled') NOT NULL,
  created_at   DATETIME NOT NULL,
  INDEX (user_id, created_at)               -- enforces the 5-per-24h rule cheaply
);

CREATE TABLE wallets (
  user_id   INT PRIMARY KEY,
  balance   DECIMAL(10,2) NOT NULL DEFAULT 0
);
CREATE TABLE wallet_ledger (                -- never store only a balance
  id        BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id   INT NOT NULL,
  delta     DECIMAL(10,2) NOT NULL,
  reason    VARCHAR(64) NOT NULL,           -- topup, order, refund
  order_id  INT NULL,
  created_at DATETIME NOT NULL
);
```

**The five rules that make it feel like a real store**

1. **Validate price server-side.** The browser only ever sends `package_id` and
   `quantity`; the server reads the price from `packages`. Never trust a posted
   amount — that is the single most common flaw in clone shops.
2. **Idempotency key on checkout** (a UUID per cart) so a double-tap cannot
   create two orders.
3. **`stock` checked inside a transaction** with `SELECT … FOR UPDATE`, then
   decremented — otherwise two buyers can take the last code.
4. **Wallet as ledger, not a number.** Compute balance as `SUM(delta)` or
   reconcile the running total against the ledger; a bare column drifts.
5. **Status machine**: `pending → paid → delivered`, with delivery triggered only
   by a verified payment callback (bKash/Nagad webhook), never by the browser
   returning to a success URL.

**Frontend note:** this site is Nuxt/Vue. If you want PHP, plain server-rendered
PHP + a little vanilla JS gives the same result for a catalogue store; you do not
need a JS framework. Keep the 3-step wizard as three server-rendered states so
it works without JavaScript.

## 8. What I could NOT see, and exactly why

| Missing | Cause | What would reveal it |
| --- | --- | --- |
| Real API endpoint list | lives inside the JS bundles; fetch tool returns rendered text only, and direct HTTP is blocked | a **HAR capture** from a browser's DevTools (Network tab → Save all as HAR) |
| Request/response JSON shapes | same | same HAR |
| Backend framework (Laravel? Node?) | no error pages or headers exposed; `/api` returns Nuxt's own 404 | a response header or a HAR entry for a failing `/api` call |
| Admin panel at `admin.gamesour.com` | **deliberately not probed** | out of scope; I do not enumerate other people's admin surfaces |
| Payment gateway identity | needs a real checkout, which I will not perform | would require an actual purchase |

**One HAR file closes four of those gaps at once**, and REA can read it offline:

```
rea inspect-web-network-capture capture.har --json
```

You'd capture it by: opening the site on a laptop, F12 → Network tab → reload →
click through to a product page → right-click → "Save all as HAR with content".
Attach that file and I can list every `/api/...` endpoint, its method, and its
JSON payload shape.

## 9. What I will not do

To keep this a legitimate analysis: I did not attempt login, checkout, payment,
admin access, endpoint brute-forcing, or bulk scraping of the order feed. I will
not help clone another store's user data, fake an order feed, or bypass a
premium gate. Rebuilding the *pattern* with your own content is fine; copying
their text, images, or customer data is not.
